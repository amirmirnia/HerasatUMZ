# راهنمای درخواست ملاقات و ثبت ورود

این راهنما رفتار فعلی برنامه را از ارسال درخواست توسط یک برنامه دیگر تا ثبت ورود مراجعه‌کننده توضیح می‌دهد.

## ۱. User Story

### برنامه ارسال‌کننده

به‌عنوان یک برنامه متصل، می‌خواهم نام مراجعه‌کننده، نام و کد ملی ملاقات‌شونده و تاریخ ملاقات را ارسال کنم تا درخواست ملاقات در سامانه دیدبان ثبت شود و شناسه آن را دریافت کنم.

معیارهای پذیرش:

- ارسال درخواست با کلید معتبر، یک رکورد با وضعیت `Pending` ایجاد می‌کند.
- پاسخ موفق شامل شناسه درخواست و پیام ثبت است.
- درخواست بدون کلید یا با کلید نامعتبر، پاسخ `401` دریافت می‌کند.
- ثبت مجدد برای همان کد ملی ملاقات‌شونده، در فاصله کمتر از زمان تنظیم‌شده، پاسخ `429` دریافت می‌کند.

### نگهبان یا کاربر پنل

به‌عنوان کاربری که به «ثبت ملاقاتی» دسترسی دارد، می‌خواهم درخواست‌ها را ببینم، با انتخاب «ثبت ورود» اطلاعات موجود را به فرم منتقل کنم و پس از دریافت بقیه اطلاعات از مراجعه‌کننده، ورود او را ثبت کنم.

معیارهای پذیرش:

- فهرست درخواست‌ها برای کاربران واردشده با همان دسترسی ثبت ملاقاتی قابل مشاهده است.
- جستجو بر اساس نام مراجعه‌کننده، نام ملاقات‌شونده یا کد ملی ملاقات‌شونده انجام می‌شود.
- فهرست از جدیدترین رکورد مرتب می‌شود و هر صفحه ۲۰ رکورد دارد.
- انتخاب «ثبت ورود» فقط فرم را باز و پر می‌کند؛ در این مرحله ورود ثبت نمی‌شود.
- پس از ذخیره موفق فرم، وضعیت درخواست در دیتابیس `Entered` می‌شود.
- رکورد در فهرست باقی می‌ماند و دکمه غیرفعال «ورود شد» نمایش داده می‌شود.
- ثبت مجدد ورود برای همان درخواست در سرور رد می‌شود، حتی اگر فرم از قبل در تب دیگری باز بوده باشد.
- اگر ثبت نهایی خطا دهد، وضعیت درخواست نباید به‌تنهایی تغییر کند.

## ۲. تعریف افراد و داده‌ها

| فیلد | مفهوم |
|---|---|
| `hostFullName` | نام فردی که قرار است با او ملاقات شود |
| `hostNationalCode` | کد ملی ملاقات‌شونده |
| `visitorFullName` | نام فردی که مراجعه می‌کند |
| `requestedDate` | تاریخ درخواستی ملاقات، به فرمت میلادی `yyyy-MM-dd` |

`hostNationalCode` متعلق به ملاقات‌شونده است. فیلد `NationalCode` در فرم ثبت ملاقاتی متعلق به مراجعه‌کننده است؛ این دو نباید جایگزین هم شوند.

## ۳. جریان کار

1. برنامه دیگر درخواست را با HTTPS و هدر `X-API-Key` ارسال می‌کند.
2. `ApiKeyAuthenticationHandler` کلید را بررسی می‌کند.
3. کنترلر، ورودی را با MediatR به `CreateMeetingRequestCommand` می‌فرستد.
4. Handler محدودیت زمانی همان کد ملی را بررسی می‌کند و درخواست را با وضعیت `Pending` ذخیره می‌کند.
5. برنامه ارسال‌کننده پاسخ `201` و شناسه درخواست را دریافت می‌کند.
6. نگهبان از منوی «درخواست‌های ملاقات» به `/panel/meeting-requests` می‌رود.
7. دکمه «ثبت ورود»، فرم زیر را باز می‌کند:

   ```text
   /panel/visitors/create?meetingRequestId=125
   ```

8. فرم جزئیات درخواست را از API پنل دریافت می‌کند و نام مراجعه‌کننده و ملاقات‌شونده را پر می‌کند.
9. کد ملی ملاقات‌شونده و تاریخ شمسی درخواست، جداگانه بالای فرم نمایش داده می‌شوند.
10. نگهبان کد ملی مراجعه‌کننده، شماره تماس و سایر اطلاعات لازم را دریافت و تکمیل می‌کند.
11. فرم، `MeetingRequestId` را همراه اطلاعات ثبت ورود به `POST /api/visitors/register` می‌فرستد.
12. `RegisterVisitorCommandHandler` اطلاعات ورود را ذخیره و وضعیت درخواست را `Entered` می‌کند.
13. کاربر به فهرست درخواست‌ها برمی‌گردد و دکمه «ورود شد» را می‌بیند.

انصراف از فرم، وضعیت درخواست را تغییر نمی‌دهد.

## ۴. تنظیمات برنامه مقصد

بخش زیر در `HerasatUmz/Server/appsettings.json` قرار دارد:

```json
{
  "MeetingApi": {
    "ApiKey": "",
    "RequestIntervalMinutes": 1
  }
}
```

این قطعه فقط بخش مرتبط از تنظیمات را نشان می‌دهد؛ تنظیمات موجود برنامه باید حفظ شوند.

- `ApiKey`: کلید مشترک برنامه مقصد و برنامه ارسال‌کننده. خالی بودن آن باعث رد احراز هویت می‌شود.
- `RequestIntervalMinutes`: حداقل فاصله ثبت درخواست برای یک `HostNationalCode`؛ پیش‌فرض یک دقیقه است و باید عدد صحیح بزرگ‌تر از صفر باشد.
- ملاک محدودیت، `CreatedDate` یعنی زمان ثبت درخواست در سرور است، نه `RequestedDate`.
- محدودیت به نام مراجعه‌کننده یا تاریخ ملاقات وابسته نیست؛ با تغییر این موارد، محدودیت همان کد ملی همچنان برقرار است.
- بررسی زمانی، درخواست‌های قبلی را مستقل از وضعیت آن‌ها در نظر می‌گیرد.

در محیط عملیاتی می‌توان مقادیر را از متغیر محیطی تأمین کرد:

```text
MeetingApi__ApiKey=<SECRET>
MeetingApi__RequestIntervalMinutes=1
```

کلید واقعی در سرور برنامه ارسال‌کننده نیز نگهداری شود؛ آن را در کد مرورگر، اپ موبایل، URL، لاگ یا گیت قرار ندهید.

## ۵. دسترسی‌ها

| مسیر | دسترسی |
|---|---|
| `POST /api/meeting-requests` | احراز هویت با کلید API |
| `GET /api/panel/meeting-requests` | ورود معمول کاربر پنل با JWT/کوکی |
| `GET /api/panel/meeting-requests/{id}` | ورود معمول کاربر پنل با JWT/کوکی |
| `POST /api/visitors/register` | ورود معمول کاربر پنل با JWT/کوکی |

برای صفحه فهرست، مجوز جدیدی تعریف نشده است. صفحه و API فهرست، مانند ثبت ملاقاتی، از `[Authorize]` استفاده می‌کنند. کلید API ثبت درخواست، دسترسی خواندن فهرست پنل ایجاد نمی‌کند.

## ۸. وضعیت‌ها و ارتباط با ورود

| مقدار دیتابیس | نمایش | رفتار دکمه |
|---|---|---|
| `Pending` | در انتظار بررسی | ثبت ورود |
| `Entered` | ورود شد | ورود شد، غیرفعال |

`MeetingRequestId` در DTO و Command ثبت ورود ارسال می‌شود. Handler درخواست را پیدا می‌کند و پیش از ثبت، وضعیت آن را بررسی می‌کند. پس از ذخیره، همان رکورد درخواست به `Entered` تغییر می‌کند و حذف نمی‌شود.

در مدل فعلی، `MeetingRequestId` به‌عنوان کلید خارجی در جدول `Visitors` ذخیره نمی‌شود؛ ارتباط در زمان عملیات بررسی شده و نتیجه در وضعیت درخواست نگهداری می‌شود. برای گزارش دائمی ارتباط هر رکورد ورود با درخواست اصلی، توسعه مدل و Migration جداگانه لازم است.

نمایش برچسب‌های `Approved` و `Rejected` در صفحه پشتیبانی شده، اما عملیات تأیید یا رد درخواست در این فرایند پیاده‌سازی نشده است.

## ۹. قفل و تراکنش

`MeetingRequestRegistrationGuard` از `sys.sp_getapplock` در SQL Server استفاده می‌کند:

```sql
DECLARE @result int;
EXEC @result = sys.sp_getapplock
    @Resource = @resource,
    @LockMode = 'Exclusive',
    @LockOwner = 'Transaction',
    @LockTimeout = 15000;
```

- هنگام ثبت درخواست، منبع قفل از هش کد ملی ملاقات‌شونده ساخته می‌شود.
- هنگام ثبت ورود، منبع قفل از هش مقدار `entry:{MeetingRequestId}` ساخته می‌شود.
- عملیات دیگری که همان منبع قفل را بخواهد، تا آزاد شدن آن منتظر می‌ماند؛ حداکثر انتظار قفل ۱۵ ثانیه است.
- بعد از گرفتن قفل، قواعد داخل Handler بررسی می‌شوند؛ خود Guard تصمیم نمی‌گیرد که ثبت مجاز است یا خیر.
- قفل به تراکنش تعلق دارد و با Commit یا Rollback آزاد می‌شود.
- این قفل منطقی در جدول اختصاصی ذخیره نمی‌شود؛ SQL Server آن را در مدیریت قفل‌ها نگه می‌دارد. عملیات خواندن و نوشتن همچنان قفل‌های معمول دیتابیس خود را نیز دارند.
- فقط مسیرهایی که از همین قرارداد قفل استفاده می‌کنند هماهنگ می‌شوند؛ ویرایش مستقیم جدول را مسدود نمی‌کند.
- این روش بین چند نمونه برنامه که از همان دیتابیس و منبع قفل استفاده می‌کنند نیز عمل می‌کند.

در ثبت ورود وابسته به درخواست، ذخیره اطلاعات مراجعه‌کننده، خودرو و تغییر وضعیت درخواست در یک تراکنش انجام می‌شود. خطا پیش از Commit، تغییرات دیتابیس را برمی‌گرداند. فایل‌های عکس ذخیره‌شده روی دیسک، بخشی از تراکنش SQL نیستند.

## ۱۰. سناریوهای آزمون

| سناریو | نتیجه مورد انتظار |
|---|---|
| درخواست معتبر با کلید صحیح | `201` و رکورد `Pending` |
| کلید نادرست، حذف هدر یا کلید خالی سرور | `401` و پیام تنظیمات اولیه |
| حذف نام یا تاریخ از ورودی | `400` با پاسخ JSON اعتبارسنجی |
| ارسال همان کد ملی پیش از پایان فاصله | `429` و پیام شامل تعداد دقیقه |
| ارسال کد ملی متفاوت | مستقل از محدودیت کد ملی اول |
| ارسال همان کد ملی پس از پایان فاصله | ثبت مجاز |
| دو درخواست هم‌زمان با همان کد ملی | یک ثبت؛ درخواست بعدی پس از بررسی محدودیت رد شود |
| مشاهده فهرست بدون ورود پنل | عدم دسترسی |
| انتخاب ثبت ورود | باز شدن فرم و پر شدن نام‌ها، بدون تغییر وضعیت |
| انصراف از فرم | وضعیت درخواست بدون تغییر |
| ذخیره موفق فرم وابسته به درخواست | ثبت ورود و تغییر وضعیت به `Entered` |
| باز کردن فرم درخواست واردشده | نمایش پیام ورود قبلی و جلوگیری از ثبت |
| ثبت هم‌زمان ورود از دو تب برای یک درخواست | فقط یک ورود برای آن درخواست |
| خطای ذخیره خودرو در ورود وابسته به درخواست | Rollback ثبت ورود و وضعیت درخواست |

Build کدهای این فرایند بررسی شده است؛ آزمون عملی مرورگر و آزمون تراکنش و هم‌زمانی روی SQL Server هنوز انجام نشده‌اند.
